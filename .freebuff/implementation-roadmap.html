MusicMatch — Implementation Roadmap

From ideation to a deployed product: users log in with Spotify, get a profile auto-created from their listening history, and match with others through a real compatibility score. Web app first, mobile-ready REST API.

1Where the project is today

Three generations of work: Jupyter notebooks (research) → FastAPI backend prototype (backend.py 860 LOC, database_helper.py 691 LOC) → Supabase schema (20 tables, 6 dormant). What works: manual Spotify OAuth, sync endpoints, genre pipeline (lastfm.py), genre-preference computation, persistence.

P0  Broken or dangerous
  • Real Spotify CLIENT_ID/CLIENT_SECRET hardcoded in setup.sh
  • .gitignore is UTF-16 with BOM — git parses nothing, so .env, .cache, ~700 MB datasets are untracked-but-visible
  • Compatibility score capped at 0.40 — artist_score=0.0, audio_score=0.0 hardcoded (database_helper.py:542)
  • Sync: no pagination (limit=50), blocking time.sleep, status fabricates last_synced
  • CORS allow_origins=["*"] with credentials; tokens accepted in query strings
Missing product features
  • No frontend at all
  • No first-party auth — raw tokens returned in JSON, copied via input()
  • Genre extractor not wired into sync; blocklist kills "dancehall", "big band"
  • No match / accept / reject endpoints, no chat-starter endpoints, no Blend playlist creation
  • No real test suite, no CI — test_api.py is a live-server smoke script

P0Security & repository hygiene 1–2 days · immediate

A trustworthy repo to build on. No phase starts before this lands.

  • Rotate Spotify credentials — treat setup.sh CLIENT_ID/CLIENT_SECRET as compromised; regenerate in the developer dashboard; move to tracked .env.example keys only.
  • Fix .gitignore — rewrite UTF-16 BOM → UTF-8; ignore .env, .cache, __pycache__/, dataset/, merged_tracks_features.csv.
  • Commit the backend layer — track backend.py, database_helper.py, musicmatch_client.py, test_api.py, setup.sh; fold stale docs into README.md.
  • Lock down CORS & scopes — replace allow_origins=["*"] with an env allowlist; trim SPOTIFY_SCOPE.
  • Archive orphans — xanadu.py, spider __pycache__ remnants, pdfs/; keep ~700 MB datasets out of git.
Acceptance: no secret string in any tracked file; git check-ignore .env succeeds; fresh clone + pip install -r requirements.txt starts the backend; rotation confirmed in Spotify dashboard.

P1Auth & account model — login 1 week

"Users can login" — a stable MusicMatch account per Spotify login. Foundation for everything after it.

  • Spotify OAuth 2.0 authorization-code + PKCE — /auth/login → /auth/callback exchanges code server-side; kill raw-token-in-JSON + input() copying; store refresh token encrypted at rest.
  • User document identity — users/{spotify_id} created on first login. No foreign keys in NoSQL: the latent FK violation in create_or_update_user (database_helper.py:48) disappears with the schema; data is denormalized into documents, so models evolve field-by-field with zero migrations.
  • Access control — MongoDB stays backend-only (MONGODB_URI server secret + our JWT middleware); users never get DB credentials. Firestore alternative: versioned security rules + Admin SDK — same middleware pattern.
  • First-party JWT for API clients — POST /api/v1/auth/token → access + refresh; all /api/v1/** use Authorization: Bearer; never tokens in query strings or bodies.
Acceptance: clean browser → login → GET /api/v1/me works with no token in the URL; a users/{spotify_id} doc exists; unauthenticated = 401; tokens and MONGODB_URI never logged.

P2Sync engine correctness — listening history 1–1.5 weeks

Complete, observable, rate-limit-safe ingestion — the raw material for every profile.

  • Pagination — loop offset past every limit=50 fetch: top tracks/artists (3 windows), saved tracks/albums, playlists.
  • Real background execution — replace blocking time.sleep(0.5) in _background_sync_all_data (backend.py:237) with asyncio.sleep / a queue.
  • Real sync status — persist job rows (status, counts, timestamps, error) instead of fabricating last_synced (backend.py:293); frontend polls it.
  • Rate-limit & retry — honor Retry-After on 429, backoff on 5xx, per-user serialization.
  • Batch writes — kill the N+1 storm in upsert_track/upsert_track_artists (database_helper.py:135, :203) with ordered bulkWrite upserts; delete-then-insert → replace-one/transaction.
  • Idempotency — re-running a sync yields identical data.
  • Genre extraction in the loop — run GenreExtractor.extract_genres (lastfm.py:27) during sync, not just the manual endpoint; fix blocklist regexes killing "dancehall"/"big band".
Acceptance: a 2,000+ track user syncs to 100% with zero loss; status shows genuine progress; concurrent syncs don't duplicate rows; re-sync is a no-op diff; all artists get genres.

P3Auto-profile & compatibility scoring 1–1.5 weeks

"Create a profile (or make one for them)" + a real compatibility score. Today's math can never exceed 0.40.

Auto-generated profile (zero user input)

  • Genre fingerprint — weighted vector from compute_user_genre_preferences (database_helper.py:336, weight w=(N−p+1)/N).
  • Top artists / tracks / eras from the three time windows; audio-feature fingerprint (energy, valence, danceability, tempo…) → plain-language sound blurb.
  • Music personality deterministic template (v1); visibility controls; legacy SQL leftovers (user_preferences, user_audio_preferences, user_saved_albums) become fields or subcollections on the user document — embed vs. subcollection per access pattern.
  • Endpoints: GET /api/v1/me/profile, public GET /api/v1/users/{id} respecting visibility.

Remove the 0.40 cap

  • Artist score (0.3) — weighted Jaccard over top-200 artists: Σ min(wₐ,w_b) / Σ max(wₐ,w_b).
  • Audio score (0.3) — cosine similarity of normalized audio-feature centroids (replace the hardcoded 0.0s at database_helper.py:542).
  • Overall = 0.4·genre + 0.3·artist + 0.3·audio ∈ [0,1], computed in application code (no SQL RPCs) and persisted as a score document with a component breakdown so the UI can explain the match.
Acceptance: identical histories → ≥ 0.95; disjoint → ≤ 0.1; genre-only fixture proves the 0.40 cap is gone; profile renders complete with no user input.

P4Matching product surface 1 week

Users see and act on matches.

  • Candidate discovery — v1 pairwise batch (nightly + on new users, fine to ~10k users); v2 Atlas Vector Search / ANN when O(n²) grows.
  • Endpoints — GET /api/v1/matches (ranked + breakdown + headline); POST …/accept · …/reject writing users/{id}/swipes + matches/{pair_id} (mutual accept = match); GET …/chat-starters surfacing generate_chat_starters(); DELETE … unmatch.
  • Blend playlist creation — matched pair → collaborative playlist via Spotify Web API: union of top tracks re-ranked by pairwise score; store blend_playlist_id.
  • Freshness — invalidate a user's score rows when they re-sync.
Acceptance: two known-overlap accounts see each other ranked; mutual accept → match; chat starters cite a genuinely shared artist; one tap creates a playlist visible in both Spotify accounts.

P5API contract hardening — mobile-ready 3–5 days · interleaved

One stable, documented API for web now and mobile later.

  • Version & envelope — all product endpoints under /api/v1; uniform response shape; fix APIResponse.timestamp evaluated once at import (backend.py:119).
  • Cursor pagination on list endpoints; consistent JSON error model with proper HTTP codes.
  • Logging — structured logging + request IDs replace print; never log tokens.
  • Validation — deprecated Query(regex=…) → pattern= (backend.py:360, 427, 637); 422 with field messages.
  • OpenAPI — FastAPI /docs is the contract; commit generated openapi.json so a mobile client can codegen; document PKCE + Bearer flow.
  • CORS for SPA — explicit origins + credentials + Authorization header.
Acceptance: a stranger builds a minimal client from openapi.json alone; every endpoint is Bearer-authenticated; no token in any URL, body, or log line.

P6Web frontend 2–3 weeks

A real user completes login → profile → match. Stack: Next.js (App Router) + TypeScript + Tailwind on Vercel, talking only to /api/v1.

  • / landing → "Log in with Spotify" (starts PKCE) · /onboarding/sync live progress polling real job status · /profile auto-profile with visibility controls
  • /matches ranked candidates with score-breakdown bars (genre/artist/audio) · /matches/[id] shared-taste highlights, chat starters, Make Blend playlist button · /settings re-sync / disconnect
  • UX: profile usable before writing anything; loading/empty/error states; mobile-responsive.
Acceptance: a cold user on a fresh browser logs in → watches real sync progress → sees a full profile → matches → creates a Blend playlist, with no manual token pasting.

P7Deployment 3–5 days · after P1

  • Backend — Docker → Render / Fly.io / Railway; uvicorn backend:app; healthcheck /health.
  • Database — MongoDB Atlas free tier → paid (alt: Firebase Firestore); MONGODB_URI in platform secrets only; collections auto-create on first write; indexes via migrate-mongo; backups on.
  • Frontend — Vercel (NEXT_PUBLIC_API_URL); exact-match Spotify redirect URIs for prod + local.
  • Environments — staging + prod with separate DBs; secrets in platform env only (.env.example tracked, .env never); log aggregation, error alerting, uptime check.
Acceptance: a stranger opens the prod URL and completes the full P6 flow; no secret in repo or client bundles; rollback = redeploy previous image.

P8Testing & CI ~1 day bootstrap · continuous

  • Unit (pytest) — genre fixtures + blocklist regressions ("dancehall", "big band" survive); compatibility fixtures (identical ≥ 0.95, disjoint ≤ 0.1, cap gone, UUID-swap invariance); profile derivation; sync pagination/idempotency against a mocked Spotify client.
  • Integration (opt-in) — mark test_api.py as @pytest.mark.integration, only with server + credentials.
  • GitHub Actions — on PR: black --check, flake8, pytest, later npm run build; no network in default tests.
Acceptance: pytest green locally and in CI with no external services; a PR breaking the score math or blocklist fails CI.
